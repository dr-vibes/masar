# بروتوكول العمل بالذكاء الاصطناعي | Context Engineering / Vibe Coding

## الهدف
إبقاء سياق مشروع مسار **قابلًا للاستعادة من الملفات** بدل الاعتماد على ذاكرة محادثة واحدة؛ كل تعديل يجب أن يكون قابلًا للتدقيق والاستئناف والتراجع.

## بداية كل جلسة
1. اقرأ `PROJECT_CONTEXT_AR.md`, `AGENTS.md`, `docs/HANDOFF_AR.md` وأحدث قيود `CHANGELOG.md`.
2. افحص الشفرة الفعلية/الإعداد المعني قبل اقتراح التعديل؛ لا تعتمد على وثائق قد تكون قديمة وحدها.
3. عرّف مهمة محدودة ومعيار نجاح/خطر/خطة رجوع؛ اختَر خطوة واحدة فقط إذا كانت على خادم AWS.
4. لاحظ ثلاث حالات دائمًا: **مطبق في المصدر محليًا** / **دُفع إلى GitHub** / **نُشر على AWS**؛ لا تختزلها في «تم».

## أثناء التنفيذ
- اختر تعديلًا صغيرًا سهل التراجع، وحافظ على وظائف مسار الحالية. استخدم طلب دمج/فرع Git عند توفر المستودع.
- سجل ما حدث فورًا في `CHANGELOG.md`، حتى لو كان تغييرًا يدويًا في إعداد AWS أو اختبارًا فشل. استخدم `docs/CHANGE_TEMPLATE_AR.md`.
- لو ظهر خطأ أثناء الأوامر: سجّل نصه غير الحساس، لا تخترع سببًا، أصلح الخطوة الحالية قبل المتابعة.
- لا تعرض أمرًا متعدد العمليات مؤثرة قبل أن تنجح الخطوة الأولى على الخادم (إلا إذا كان التحقق جزءًا ضروريًا لا يمكن تجزئته).
- عند التغيير البرمجي: `npm test` ثم `npm run build`، وأضف اختبارًا للخاصية أو الخطر الجديد.
- عند تغيير الحسابات: اختبارات حدودية مع نتائج مالية مرجعية، ومصادر نسب، وشرح سبب الاختلاف وعدم يقين النتائج.

## نهاية كل جلسة/تسليم
- حدِّث **السجل الإلزامي** `CHANGELOG.md` مع المعرف والتاريخ والدليل وطريقة الرجوع.
- حدِّث `docs/HANDOFF_AR.md` مع آخر حالة، الخطوة الواحدة التالية، والمخاطر والقرارات المطلوبة.
- إذا تغيّرت المعمارية/الأمن/الاستضافة/النطاق أو الأولويات، حدّث المستند المتخصص نفسه.
- اذكر صراحة ما لم تنفذه أو تتحقق منه؛ لا تستبدل ذلك بعبارة «يعمل تمامًا».
- احفظ التوثيق داخل المشروع ونسخة Git المحدثة؛ **التوثيق الموجود في ZIP وحده لا ينعكس تلقائيًا على AWS أو GitHub**.

## صيغ قياسية
- مداخل المهام: `TASK-YYYYMMDD-NN` (يمكن العمل دون ID مؤقت، لكن سجل التشغيل يجب أن يحمل معرفًا).
- سجل التغييرات: `CHG-YYYYMMDD-NN`.
- قرار هندسي مهم: `ADR-NNN` في `docs/DECISIONS_AR.md`.
- حالات: `مخطط` / `نُفذ محليًا` / `مطبق على الخادم` / `مؤكد باختبار` / `معلّق` / `متراجع عنه`.

## قاعدة عدم فقد السياق
أي ادعاء جديد عن إعداد خادم أو تعيين نطاق أو شكل البيانات لا يُعد حقيقة ثابتة إلا إذا كان مستندًا إلى كود/أوامر مخرجات/صورة موثقة. وإذا تغيّرت الحالة، **حدّث السياق والسجل فورًا** ولا تترك معلومتين متناقضتين بلا تفسير.

## الفحص الآلي في GitHub (مضاف إلى المصدر؛ لم يثبت تفعيله بعد على مستودع بعيد)
- `npm run docs:check`: يفحص وجود الملفات المرجعية الأساسية وسجل تغيير مؤرخ.
- `.github/workflows/quality.yml`: يشغّل `npm ci` و`npm test` و`npm run build` وفحص التوثيق، ويشترط في طلبات الدمج تحديث `CHANGELOG.md` و`docs/HANDOFF_AR.md` إذا تغير أي ملف آخر.
- الفحص الآلي يُقلل النسيان لكنه لا يتحقق من **صدق** المعلومات؛ يعتمد أيضًا على مراجعة بشرية ودليل فني.
